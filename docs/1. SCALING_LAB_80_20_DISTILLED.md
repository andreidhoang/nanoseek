## MODULE A: THE SCALING LAW LABORATORY (60% of effort)

### This Is THE Differentiator. Nothing Else Comes Close.

**Why 60%:** This is the single highest-value skill for the role. The posting says
"Design and run experiments to improve training efficiency, reduce step time,
increase uptime, and enhance model performance." The way you design experiments
at frontier scale is: you run them SMALL first, fit a scaling law, predict the
outcome at large scale, then validate. If your prediction is wrong, you don't
spend $10M on a bad idea.

Nobody in the applicant pool has this. Nobody. Because it requires actually
training 15-20 models systematically and doing the math.

### What You Build:

```python
# The entire module is ~500 lines of experiment orchestration + analysis code.
# The MODEL code is NanoGPT or Llama reference — you don't write that.

scaling_law_lab/
│
├── configs/
│   └── sweep.yaml          # 15-20 (N, D) configurations
│                            # N ∈ {10M, 25M, 50M, 100M, 200M, 400M, 800M}
│                            # D ∈ {200M, 500M, 1B, 2B, 5B, 10B, 20B, 50B}
│                            # Each (N,D) pair = one training run
│                            # Total: ~15-20 runs, selected to cover the space
│
├── train_run.py             # Thin wrapper around NanoGPT/Llama training
│                            # Logs: final_loss, N, D, compute_used, step_time
│                            # Uses W&B for all logging
│                            # KEY: identical hyperparameters across all runs
│                            # (this is the muP insight — LR must transfer)
│
├── fit_scaling_law.py       # THE CORE: ~150 lines
│   │
│   ├── Collect (N, D, L) triples from all runs
│   ├── Fit L(N,D) = E + A/N^α + B/D^β via scipy.optimize
│   │   ├── Use Huber loss (robust to outliers from failed runs)
│   │   ├── Initialize with Chinchilla values as warm start
│   │   └── Compute confidence intervals via bootstrap
│   │
│   ├── Compute optimal allocation:
│   │   ├── Given C, solve for N*, D* that minimize L
│   │   └── Compare to Chinchilla ratio (≈20 tokens/param)
│   │
│   └── Generate scaling law plots:
│       ├── Loss vs N at fixed D (parameter scaling)
│       ├── Loss vs D at fixed N (data scaling)
│       ├── Optimal N* and D* vs compute budget C
│       ├── IsoFLOP curves with optimal frontier
│       └── Predicted vs actual loss for validation run
│
├── predict_and_validate.py  # THE MONEY SHOT
│   │
│   ├── Use fitted law to predict loss at (7B, 140B tokens)
│   ├── Train the 7B model (this is the expensive run)
│   ├── Compare predicted vs actual loss
│   ├── Report: prediction error, confidence interval
│   └── If <2% error: scaling law is validated
│
├── inference_aware.py       # BONUS: Beyond Chinchilla
│   │
│   ├── Add inference cost to the optimization:
│   │   total_cost = C_train + C_inference × num_queries
│   │   Solve for N* that minimizes total_cost for given quality target
│   ├── This shows you understand WHY Llama 3 overtrained on 15T tokens:
│   │   smaller model + more data = same quality + cheaper inference
│   └── Plot: optimal N as function of expected inference volume
│
└── report/
    └── SCALING_LAW_REPORT.md  # Publication-quality writeup
        ├── Mathematical derivation of L(N,D)
        ├── All plots with proper axes, legends, error bars
        ├── Comparison to Chinchilla and Kaplan exponents
        ├── Analysis: "My exponents differ because [specific reason]"
        └── Section: "Inference-aware optimal scaling"
```

### Critical Detail: muP (Maximal Update Parameterization)

For the scaling law to work, hyperparameters MUST transfer across scales.
This means you need:

```python
# Key muP rules (you implement these as a config, not a framework):
# 1. Initialize weights: std = 1/√fan_in (standard)
# 2. Output logit layer: multiply LR by 1/width
# 3. Attention logits: scale by 1/d instead of 1/√d
# 4. LR for hidden layers: scale with 1/width
#
# In practice: set base_lr at 125M, then scale it for each model size.
# If muP is correct, the SAME effective learning rate works at all scales.
# Validate: plot optimal LR vs model size. Should be flat with muP.
```

## MODULE B: TRAINING STABILITY ENGINE (25% of effort)

### Why This Second:

The posting says "respond to on-call incidents during model launches, diagnosing
problems quickly." At 3 AM when the loss spikes, you need to know EXACTLY which
technique to apply. This module builds that muscle memory.

### What You Build:

```python
stability_engine/
│
├── experiments/
│   │
│   ├── spike_reproduction.py     # ~80 lines
│   │   # Deliberately cause loss spikes by:
│   │   # 1. Injecting a batch of garbage data (random tokens)
│   │   # 2. Setting β₂=0.999 (too high, accumulates bad momentum)
│   │   # 3. Using too-large learning rate
│   │   # 4. Removing gradient clipping
│   │   # 5. Using FP16 instead of BF16 (range overflow)
│   │   # For each: log the spike, capture gradient norms, activation stats
│   │
│   ├── stability_techniques.py   # ~200 lines, THE CORE
│   │   # Implement 5 proven techniques ON TOP of standard training:
│   │   #
│   │   # 1. QK-Norm: normalize Q,K before attention
│   │   #    - torch.nn.functional.normalize(q, dim=-1)
│   │   #    - Measure: % of runs that spike with/without
│   │   #    - Tradeoff: measure long-context perf degradation
│   │   #
│   │   # 2. Logit softcapping (Gemma-style):
│   │   #    - logits = soft_cap * tanh(logits / soft_cap)
│   │   #    - Prevents attention logit overflow
│   │   #    - Typical soft_cap = 50.0
│   │   #
│   │   # 3. Z-loss: auxiliary penalty on large logits
│   │   #    - z_loss = 1e-4 * log(sum(exp(logits)))²
│   │   #    - Prevents logit drift without changing model behavior
│   │   #
│   │   # 4. Embedding scaling: multiply embeddings by √d_model
│   │   #    - From "Spike No More" paper
│   │   #    - Satisfies "large residual" stability condition
│   │   #
│   │   # 5. Adam β₂ tuning: 0.95 vs 0.999
│   │   #    - 0.95 = faster forgetting of bad gradient moments
│   │   #    - Most frontier models use 0.95 (GPT-3, Llama, etc.)
│   │
│   └── ablation_matrix.py        # ~100 lines
│       # Run a small model (125M) with ALL 2^5 = 32 combinations
│       # of the 5 techniques on/off
│       # Measure: spike frequency, final loss, training throughput
│       # Result: which combinations are necessary and sufficient?
│       # Expected finding: QK-norm + β₂=0.95 + embed_scale = sufficient
│       #   (z-loss and softcap are redundant if you have these three)
│
├── spike_detector.py             # ~60 lines
│   # Real-time monitoring during training:
│   # - Track rolling mean and std of loss
│   # - Spike = loss > rolling_mean + 5 * rolling_std
│   # - Also track: gradient norm spike, activation NaN
│   # - Action: log to W&B with alert, optionally skip batch
│
├── auto_recovery.py              # ~80 lines
│   # When spike detected:
│   # 1. Log the bad batch indices
│   # 2. Rollback to last checkpoint (if spike > threshold)
│   # 3. Skip the problematic batch
│   # 4. Optionally: reduce LR by 50% for 100 steps, then restore
│   # This is EXACTLY what frontier labs do (see ByteDance paper)
│
└── report/
    └── STABILITY_PLAYBOOK.md
        ├── Decision tree: "Loss spiked. What do I do?"
        │   ├── Was it a data batch? → check batch loss, skip it
        │   ├── Was it gradient explosion? → check grad norm, reduce LR
        │   ├── Was it numerical? → check for NaN, switch precision
        │   └── Was it optimizer momentum? → reset Adam states (SPAM)
        ├── Ablation matrix results (table + analysis)
        └── Recommendation: "Minimum viable stability config"
```

### What This Demonstrates:

> "I systematically tested 5 stability techniques across 32 ablation
> configurations. The minimum viable set is QK-norm + β₂=0.95 +
> embedding scaling — these three eliminate 98% of spikes in my
> experiments, and adding z-loss or softcapping provides no additional
> benefit. I also built an automated spike detector with <30s latency
> and auto-recovery that rolls back and skips bad batches."

## MODULE C: PRODUCTION TRAINING OPERATIONS (15% of effort)

### Why This Third:

The posting says "own model operations, performance optimization, observability,
reliability." This module proves you can OPERATE a training run, not just
start one.

### What You Build:

```python
training_ops/
│
├── mfu_profiler.py               # ~100 lines, HIGH VALUE
│   # For ANY training run, compute:
│   # 1. Theoretical FLOPs per step: 6 * N * D_per_step (forward+backward)
│   # 2. Actual wall-clock time per step
│   # 3. MFU = theoretical_flops / (peak_flops * wall_time)
│   # 4. Gap analysis: WHERE is the missing MFU going?
│   #    - Use torch.profiler to break down step time:
│   #      forward, backward, optimizer, data loading, comm, idle
│   #    - Identify: compute-bound vs memory-bound vs comm-bound
│   # 5. Log all of this to W&B per step
│
├── step_time_optimizer.py        # ~80 lines
│   # Take the MFU gap analysis and apply fixes:
│   # 1. If data-loading bound: increase num_workers, prefetch
│   # 2. If comm-bound: tune FSDP bucket size, enable overlap
│   # 3. If memory-bound: enable activation checkpointing
│   # 4. If compute-bound: enable torch.compile, fused kernels
│   # Measure before/after step time for each fix
│
├── checkpoint_manager.py         # ~60 lines
│   # Async checkpointing that doesn't block training step
│   # Rolling window: keep last K checkpoints, delete older
│   # Checkpoint verification: load and run 1 step, compare loss
│   # Log checkpoint times and sizes to W&B
│
├── eval_harness.py               # ~80 lines
│   # Run evals every N steps during training
│   # Use lm-eval-harness (DON'T reimplement evals)
│   # Track: loss on 5 domains separately (web, code, books, math, science)
│   # Track: scaling law fit residual (is observed loss on-curve?)
│   # Alert: if loss deviates >3% from predicted scaling curve
│
└── report/
    └── TRAINING_OPS_REPORT.md
        ├── MFU breakdown for the 7B validation run
        ├── Before/after for each optimization applied
        ├── "40% of step time was X. After Y fix, step time reduced Z%."
        └── This IS the E7 report from your original roadmap
```

### What This Demonstrates:

> "On my 7B training run, initial MFU was 31%. I profiled with
> torch.profiler and found: 22% of step time was data loading stall
> (fixed with prefetch_factor=4), 14% was FSDP all-gather not overlapping
> with compute (fixed with limit_all_gathers=True), and 8% was Python
> GIL contention in my eval callback (moved to separate process).
> Final MFU: 47%. That's a 52% throughput improvement."
